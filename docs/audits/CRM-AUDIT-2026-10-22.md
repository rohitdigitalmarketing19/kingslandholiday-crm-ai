# CRM bug and security audit — 22 October 2026

Status: BLOCKED for production release. This is an audit verdict, not a claim that the application cannot run.

## Scope and method

[DOC] Read repository AGENTS.md and compared its lifecycle/security rules with the implementation. [DATA] Reviewed the Express route registrations, controllers, authentication helpers, database/schema/persistence, React CRM, separate Operations portal, payment page, document handling, PDF/theme handling, packaging, dependency manifests, and existing test scripts. Initial Git working tree was clean. No application fixes or live-data migrations were performed. No .env contents or real customer database contents were inspected.

The actual stack is React 19, TypeScript, Express, Vite and sql.js/SQLite, with optional Supabase binary database backups. There is no root composer.json or Laravel artisan application. AGENTS.md's expected Laravel/PostgreSQL architecture conflicts with the repository. Preserve the existing stack pending an owner decision; do not interpret this audit as authorization to rewrite it. PRODUCT.md, DESIGN.md and the named architecture/gap documents were not found in the repository inventory.

An isolated synthetic database under `.audit-runtime` was used for reproductions. HTTP reproductions mounted the repository's real routers in a local Express harness rather than starting the deployed entrypoint. The entrypoint was separately reviewed: its global middleware adds no authentication. No attack was run against a deployed site. Runtime impact assumes these endpoints are reachable; deployment firewall/reverse-proxy protection was not inspected.

## Ranked findings

### F01 — P0: Operational APIs lack authentication and server-side authorization

[DATA: reproduced and code] `server/index.ts`, `server/routes/users.ts`, `leads.ts`, `payments.ts`, `ops.ts`, `settings.ts`, and other route modules register operational handlers without authenticated-session/role middleware. `authenticateMiddleware` and `requireRole` appear only as definitions in `server/utils/auth.ts`. Login returns a user object rather than establishing the server-enforced session used by these routes. Frontend localStorage and sidebar permissions do not enforce access.

Anonymous requests in the isolated harness returned HTTP 200 for the users list, database download, lead conversion, and payment confirmation. An unauthenticated caller can reach customer/finance data and administrative mutations. Fix by establishing real sessions, requiring active database-backed users for internal routes, and enforcing record ownership plus action permissions. Explicitly separate public payment/client-detail routes from staff APIs.

### F02 — P0: Plaintext passwords are stored and returned to callers

[DATA: reproduced and code] `server/routes/users.ts`, especially `formatUserRow`, login, create and update handlers, stores and compares plaintext passwords and includes `password` in user responses. Anonymous GET `/api/users` returned a populated password field. The generic update route can change passwords without the separate OTP flow. Listing an empty user table also provisions a predictable fallback admin; GET additionally deletes selected legacy users. These are both confidentiality and state-changing-GET defects.

Hash passwords using the existing scrypt helper or a supported password library, remove password values from every response/email, remove production default credentials, and move provisioning/cleanup to an explicit controlled workflow. Existing deployed credentials should be considered exposed if these endpoints were publicly reachable; rotate them after closing the leak. Actual historical access is unknown.

### F03 — P0: Admin identity can be forged for customer documents and client details

[DATA: reproduced helper + code] `server/controllers/clientDocumentsController.ts:getRequesterInfo` accepts `x-user-role: Admin` without a verified session, or looks up any caller-supplied `x-user-id`. The forged header returned `isAdmin: true` in the harness. `clientDetailsController.ts` reuses this helper. This defeats the apparent protection on passport/Aadhaar/PAN uploads, listing, signed-ticket issuance, downloads, edits and deletion. Document byte-type checks and short-lived tickets do not repair the missing authenticated identity.

`server/controllers/pdfThemesController.ts:isAdminUser` additionally returns true even when identity headers are absent. Bind all identity and admin decisions to authenticated server state; deny by default. Document-ticket and JWT secrets also have hard-coded fallbacks; require configured production secrets.

### F04 — P0: Complete database download and replacement are exposed

[DATA: reproduced download + code] `server/routes/settings.ts` exposes backup download, listing, creation and restore without authentication. Anonymous database download returned HTTP 200 in isolation. Restore-upload accepts a supplied SQLite image and installs it; migration errors are swallowed afterward. An attacker could obtain all stored data or replace it. No destructive restore was attempted. Restrict these endpoints to explicit administrative abilities, validate restore compatibility before replacement, and retain a verified recovery path.

### F05 — P0: Provider secrets are exposed and payment destinations can be changed

[DATA: code] `paymentsController.ts:getPaymentSettings` returns the entire payment_settings row including `key_secret`; `settingsController.ts:getAgencySettings` returns `smtp_pass`. Their settings GET/POST/PUT routes are unauthenticated. Storage is plaintext SQL text. A caller can read configured credentials or replace bank/UPI destination details. Actual live credential configuration was intentionally not inspected.

Return only approved public checkout settings to customers. Encrypt server credentials at rest, mask them in staff views, restrict and audit changes, and never send secrets to the browser. Rotate any configured credentials if these APIs were exposed.

### F06 — P0: Customer claims and gateway fallback can manufacture paid receipts

[DATA: reproduced and code] `components/PaymentPageView.tsx:handleSubmitPayment` creates a customer submission and immediately calls `/api/payments/confirm`. `triggerRazorpayCheckout` calls that same success path with a fabricated reference when the Razorpay script is unavailable. The server accepts a reference and amount without provider signature verification. There is no verified gateway event/idempotency boundary in these routes.

The isolated anonymous request marked a ₹1,000 link Paid with `paid_amount = 5000`. A nonexistent payment key also returned HTTP 200 with `success: true`. Public submissions must remain Pending Review. Provider receipts require server-side authenticity and amount validation; manual confirmations require an authorized actor and evidence. Missing provider scripts must show failure/unavailable state.

### F07 — P1: Payment history is mutable, unbounded and split across tables

[DATA: code and excessive-confirmation reproduction] `paymentsController.ts:saveInstallmentSchedule`, `updateInstallmentStatus`, and `confirmPaymentLink` overwrite paid amounts/status/reference data and use INSERT OR REPLACE; schedule edits accept client-supplied paid state. They synchronize several tables using separate persisted writes and broad swallowed errors. `clearAllPaymentSubmissions` hard-deletes the submission history. There is no booking-liability aggregate lock or append-only verified receipt ledger in this path. Money columns are SQLite REAL and calculations use JavaScript numbers.

Confirmation retries can overwrite evidence; partial cross-table failure can produce conflicting balances. Implement authoritative immutable booking totals, integer-paise or decimal money, append-only receipts/voids, uniqueness/idempotency constraints and atomic aggregate validation. Keep expectations and submissions separate from receipts.

### F08 — P1: Conversion bypasses accepted proposals and accepted revenue is not frozen

[DATA: reproduced and code] `leadsController.ts:updateLeadStatus` accepts arbitrary status values; Closed Won triggers `syncConvertedLeadsToOps` without an accepted proposal. A new synthetic lead converted successfully with no quote. `quotesController.ts` edits quotes in place without historical versions/acceptance locks. Operations sync selects the latest quote and overwrites `ops_customers.total_amount`.

Editing the synthetic quote from ₹1,000 to ₹9,000 changed the converted Operations total to ₹9,000. There is no canonical accepted-proposal booking snapshot in the inspected schema. Enforce transitions centrally and introduce the accepted-version → immutable booking → trip chain through a reviewed compatibility/migration plan.

### F09 — P0: Reading Operations can delete operational history

[DATA: reproduced and code] `opsController.ts:getAllOpsCustomers`, `getAllOpsVouchers`, and `getAllOpsItineraries` invoke sync during list requests. Sync deletes Operations customers not currently in its converted-lead set, along with itineraries and installments; voucher foreign-key cascades can remove retained child records when the parent is deleted. It also removes vouchers missing from the latest quote and resets files when hotel names change.

After the synthetic lead changed from Closed Won to Lost, listing Operations deleted its Operations customer. Reads must be side-effect free. Cancellation/status changes must preserve financial/document history using explicit controlled transitions, not reconstruct/delete operational records from current lead status.

### F10 — P1: Empty Operations lists inject demo bookings into the real database

[DATA: reproduced and code] `getAllOpsCustomers` and other list helpers call `seedOpsDefaultsIfEmpty` without an environment gate. It imports INITIAL_CUSTOMERS, vouchers and itineraries from frontend mockData and writes them to the database. The isolated list test printed default seeding and inserted demo records after cleanup removed the synthetic customer. Empty production data must remain empty; demo provisioning must be explicit and limited to development/test.

### F11 — P1: Accounts reports contract value as collected revenue and invents defaults

[DATA: code] `components/AccountsView.tsx` uses `c.totalAmount` or a ₹55,000 fallback as `totalPkg`, then sums `t.totalAmount` into `totalCustomerPaid`. Margin is calculated from that contract value minus mutable hotel/cab paid amounts, rather than verified customer collections. Other fallback branches synthesize installments and supplier breakdowns. This can show uncollected revenue and overstated realized margin. Reconcile only authoritative entries and show unknown/incomplete values explicitly.

### F12 — P1: Invoices can fabricate a paid advance and UTR

[DATA: code] `operations-team-portal/src/components/InvoiceModule.tsx` creates a 30%/50%/balance schedule when no installments are available, labels the first installment PAID, dates it in the past and generates a random UTR. This can put nonexistent receipt evidence into a customer-facing document. Invoice configuration is stored in browser localStorage rather than a durable issued-invoice snapshot in this path. Remove fabricated payment evidence and require explicit persisted invoice issuance with authoritative tax/company/customer snapshots and identity.

### F13 — P1: Vendor payout history and trip completion can be overwritten directly

[DATA: code] `opsController.ts:updateOpsCustomer` permits direct updates to hotel/cab costs, paid fields/statuses and trip status. Voucher amounts/payment statuses are similarly mutable. These paths do not implement an append-only supplier disbursement/void ledger or prevent exceeding obligations. `operations-team-portal/src/App.tsx` completes trips through a general customer update with `status: Completed`; there is no controlled completion dependency/aggregation transaction in that path. The checklist-based upcoming view does not prove real voucher, driver or payment dependencies. Add authorized domain actions, obligations, payout entries, dependency validation and idempotent completion.

### F14 — P2: Delivery and save state can claim success without a completed external/persistent action

[DATA: code] Operations `handleSendVoucherToCustomer` persists Sent to Customer before opening a WhatsApp deep link; no provider delivery confirmation or attached-file evidence is recorded. Missing phone numbers use a fixed fallback recipient. Operations save/update catch handlers write the requested result into React state/localStorage even after API failure, so a failed server save can appear successful until refresh or on another device. Preserve truthful pending/failed state and distinguish message preparation from confirmed delivery.

### F15 — P1: Persistence can acknowledge writes that were not durably saved

[DATA: code; failure injection not run] `server/db/connection.ts` keeps an in-memory SQLite database and synchronously exports the whole file for each modifying query. `saveDb` catches disk-save failures and only logs them, allowing callers to return success. `safeWriteBuffer` can redirect failed writes to a different fallback database path. Separate server processes can each retain stale in-memory copies and overwrite each other's snapshots; this concurrency risk is an inference, not a reproduced production incident. Use one approved durable database strategy and surface failed commits; do not change production storage without a reviewed data migration.

### F16 — P1/P2: Dependency audit flags vulnerable locked packages

[DATA] Online root `npm audit --json` reported 10 affected package entries: 3 critical, 3 high, 3 moderate, 1 low. Critical: proxy-addr, shell-quote, concurrently. High: nodemailer, source-map-js, vite. Moderate: body-parser, express, qs. Low: dompurify. This counts dependency entries, including inherited findings, not ten demonstrated application exploits. Runtime reachability and dev-only exposure need individual assessment. Full advisory evidence is in `npm-audit-2026-10-22.json`. No automatic dependency fix or major upgrade was run. The separate portal audit was interrupted and is not claimed as completed.

### F17 — P2/P3: Proposal acceptance regressions and large frontend bundles

[DATA] Existing `scripts/run-acceptance-tests.ts`: 5 passed, 5 failed (tests 1, 4, 5, 7, 8). These cover inclusion/exclusion continuation, long day splitting, no-image expectations and short/long terms pagination. They are string/structure assertions; failures require visual reproduction before every assertion is treated as a confirmed layout defect. No realistic PDF was visually rendered in this audit. Both production builds warn about oversized chunks: root main JS approximately 3.50 MB and portal approximately 2.17 MB before gzip. Loading and interaction performance have not been measured.

### F18 — P2: Quote parent mismatch can recurse until stack exhaustion

[DATA: code; not runtime reproduced] `quotesController.ts:createQuote` detects an existing quote ID globally and calls updateQuote with the requested lead. `updateQuote` checks that ID under the requested lead and calls createQuote if it is absent. Supplying a quote ID belonging to another lead therefore cycles between these functions. Reject ID ownership conflicts explicitly; do not use recursive upsert fallbacks.

## Repair order

1. Restrict exposure of the current application while P0 issues are fixed. Introduce real authentication, active-user checks, record scopes, and administrative abilities; protect backup/reset/settings/document routes.
2. Hash/remove exposed passwords and secrets, eliminate default production credentials and fake payment success, then rotate affected deployed secrets.
3. Establish immutable accepted-proposal booking identity and verified append-only customer/vendor ledgers; enforce amount limits, atomic transactions, idempotency and financial correction history.
4. Remove destructive sync and automatic demo seeding from reads; preserve historical operations/vouchers through explicit transitions.
5. Correct invoices/accounts/delivery/completion, resolve dependency advisories, and add a full negative-path and lifecycle regression suite before visual polishing.
